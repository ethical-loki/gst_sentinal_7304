1. Authentication Module:
Overview
To access the API, application should first authenticate using the credentials. The credentials have to be generated by the taxpayers and get the auth token issued. Same auth token is to be used to access subsequent APIs. Validity of the auth token will be 360 minutes (60 minutes on Sandbox for ease of testing). Any hits to this API within these 360 minutes will return the same token, hence there is no need to hit the API unless the token has expired. However, there is a provision to forcefully generate a new token within the last 10 minutes of expiry by calling this API with "ForceRefreshAccessToken" set to "True". On expiry, same authentication API needs to be invoked to issue new auth Token.

The format and details of a sample API request is depicted in following table.

URL: <URL>/v1.04/auth
Content-Type: application/json
Method: POST

Request Header
Attributes    Description
client_id     client id to be provided by E-Invoice System
client_secret client secret to be provided by E-Invoice System
Gstin         GSTIN of the authenticated user

Request Payload
Data: Json containing the Credentials is encoded using Base64 and then encrypted using e-Invoice public Key
Attributes	             Description
UserName                 Username of Tax payer as created on E-Invoice portal for API Integration
Password	          Password of Tax payer as in E-Invoice portal for API Integration
AppKey	                Any random 32 bytes array, generated by user. On converting to String using base 64 encoding will be 44 chars long.
ForceRefreshAccessToken	The value of this attribute to be set true, if client needs to refresh the token 10 minutes before expiry

Response Payload
Attributes	                   Description
Status	                       Status of the authentication request(values 1-Success and 0 Failure)
Data	                       If Status is ‘1’
ClientId	                   Client Id
UserName	                   User Name
AuthToken	                   Authorization token
Sek	                           Session Encryption Key generated using AES 256(AES/ECB/PKCS7Padding) algorithm. Encrypted () with AppKey
TokenExpiry	                   Token Expiry time. Date format is ‘yyyy-MM-dd HH:mm:ss ’
ErrorDetails	               If Status is ‘0’
ErrorCode	                   Unique error code
ErrorMessage	               Error Description
InfoDtls	                   Any additional message to be conveyed would be passed.

Validations
1. Only taxpayer GSTINs enabled for e-invoicing are allowed for authentication.


Frequently Asked Questions
1.1 Q. Getting error 'Invalid Auth Token' while generating an e-Invoice through API and it is getting expired within 6 Hours.
A. Auth Token will be active for 6 hours since the first successful login. Even if the the Auth API is called again before 6 hours, same token will be returned and the time is not reset. Hence you can generate new Auth token only when it expires after 6 hours. For example: If you have authenticated at 12:00, token will be active till 06:00 If auth API is called at 02:00, still the same token will be active till 06:00 and not till 08:00

Validations
Validations in e-Invoicing System
4.1 E-Invoice request JSON data has to be validated as per the e-Invoice JSON Schema given in the notification.
4.2 ‘Version’ attribute in the Schema is mandatory and should be latest as per the latest notification. Presently it should be passed as ‘1.1’.
4.3 IRN should not be passed as part of the request; it is generated by the e-Invoice system and sent as response.
4.4 The attributes in the JSON schema have been defined with column length, format and data types. Where-ever the data format is not defined for the attribute having data type as string, then for these attributes, the alphanumeric and special characters are allowed except the special characters “ (double quote) and \ (back slash).
4.5 IRN generation is allowed only for the active Supplier. If he is cancelled or suspended, he cannot generate IRN.
4.6 The following fields should have one of the values given in the master codes.
    4.6.1 Supply Type of Transaction
    4.6.2 Document Type
4.7 The category of transaction of "Business to Consumer (B2C)" invoices will not be considered and hence the API interface should not request for IRN for these transactions.
4.8 Document number should not be starting with 0, / and -. If so, then request is rejected.
4.9 IRN requests with Document Date from 01/04/2025 only will be accepted and processed for IRN generation. IRN requests belonging to previous dates will be rejected.
4.10 Supplier should ensure that the unique invoice number is being generated for the financial year for each invoice, in his ERP/manual system. The financial year is derived from the date of invoice. The financial year starts from 1st April and ends on 31st March.
4.11 Duplicate IRN requests are not considered. That is, if the IRN is already generated on particular type of document and document number of the supplier for the financial year, then one more IRN cannot be generated on the same combination.
4.12 e-invoice(IRN) cannot be re-generated for the cancelled e-invoice(IRN) also.
4.13 Request for the IRN/e-Invoice can be made only by the supplier of the goods or services.
4.14 In case of e-commerce transactions, the e-Commerce Operator can request for the IRN/e-invoice on behalf of the supplier. In this case, the e-Commerce Operator should have been registered on the GST portal as e-Commerce Operator and pass eCom_GSTIN accordingly.
4.15 In case the supplier is SEZ unit, then he cannot generate e-Invoice.
4.16 "Reverse Charges" can be set as "Y" in case of B2B and SEZ invoices only and tax is being paid in reverse manner as per rule. Even in case of Reverse Charged invoices, the Supplier has to generate the IRN.
4.17 SEZWP and SEZWOP supply type is allowed only if the taxpayer type of recipient GSTIN is ‘SEZ Unit’ or ‘SEZ Developer’.
4.18 Recipient GSTIN should be registered and active or suspended, on the date of preparation of the document by the supplier.
4.19 In case Recipient GSTIN is cancelled, then the document date should be between the date of registration and date of de-registration of the Recipient GSTIN.
4.20 In case SEZ Developer is Supplier, then only IGST tax rates are applicable irrespective of Supplier state code and POS code.
4.21 In case of transaction of direct export, recipient GSTIN has to be URP and state code has to be 96, PIN code should be 999999, POS should be 96.
4.22 In case of GSTIN of supplier or recipient belonging to state of ‘OTHER TERRITORY’ (with state code as 97), then PIN code can be 999999.
4.23 First two digits of the Supplier / Recipient GSTIN should match with the state code passed in the Supplier / Recipient details accordingly except if supply type is exports wherein Recipient state code will be 96.
4.24 PIN Codes are validated against the States, they belong by matching the complete pincode against state master. If the PIN Code does not exist in the master database of the e-invoicing system, and the first 3 digits of the PIN code is matched with the State as per the pattern of PIN code-to-State mapping defined by postal department, then IRN gets generated.
4.25 If "Shipping party" is provided, then the transaction is considered as "Bill To-Ship To".
4.26 If "Dispatching party" is provided, then the transaction is considered as "Bill From " Dispatch From".
4.27 If both Shipping and Dispatching parties are provided, then the transaction is considered as "Combination of Both" (Bill From - Dispatch From and Bill To- Ship To).
4.28 In case of export transactions for goods, if e-way bill is required along with IRN, then the 'Ship-To' address should be of the place/port in India from where the goods are being exported. Otherwise E-way bill can be generated later based on IRN, by passing the 'Ship-To' address as the place/port address of India from where the goods are being exported .
4.29 In case IGST on intrastate supply, tax rates and tax values related to IGST should be passed, and Supplier state code and POS state code should be same.
4.30 In case IGST on intrastate supply, then Reverse charge is mandatory.
4.31 The state code of the Supplier GSTIN and POS will decide whether the supply type is Interstate or Intrastate. That is, if the State code of Supplier and POS is same, then it is intra-state, otherwise it is inter-state. However, IGST on intrastate supply attribute will overrule this condition.
4.32 In case of Exports and SEZ, the supply is always Interstate
4.33 JSON payload size cannot exceed 2MB.
4.34 Reverse charge is not applicable for transactions if recipient taxpayer type is ISD.
4.35 Deemed exports is allowed for recipient taxpayers with taxpayer type as Regular or Casual.
4.36 Tax rate 0.5% is withdrawn.
4.37 The maximum date value for RefDtls.DocPerdDtls.InvEndDt is 31/12/2059.
4.38 The Supplier GSTIN can be of taxpayer type REG or SED.
4.39 The State code 25 of Daman and Diu is withdrawn under POS.
4.40 For RCM domestic supply type is RCMDOM and for RCM import supply type is RCMIMP. blinking New
4.41 RCM domestic and RCM import transactions are registered only by Recipient. blinking New
4.42 Reverse charge must be set as "Y" for RCM domestic and RCM import transactions. blinking New
4.43 Supplier GSTIN is always URP for RCM domestic and RCM import transactions. blinking New
4.44 RCM invoices are registered by Regular and Casual taxpayers. blinking New
4.45 Both Goods are services HSNs are allowed for RCM domestic transaction. blinking New
4.46 Only service related HSNs are allowed for RCM Import transaction.blinking New
4.47 Supplier state and POS will decide the inter/intra state transaction for RCM domestic. In case if "IgstOnIntra" flag is set as "Y", it will be treated as Inter state state transaction. blinking New
4.48 For RCM import it is always inter state transaction. blinking New
4.49 For RCM import in all the items origin country code (ItemList.OrgCntry) has to be passed and it should be same in all the items. blinking New
4.50 For RCM import supplier state code must be outside India. blinking New
4.51 SEZWP is bifurcated into SEZ with payment authorized. The supply type value is SEZWPA. blinking New
4.52 SEZWP is bifurcated into SEZ with payment not authorized. The supply type value is SEZWPNA. blinking New

Validations for e-Invoices by e-Commerce operators:
4.54 The e-Invoices may be generated by the e-Commerce operator (having tax payer type as ‘TCS’ ) on behalf of the Suppliers.
4.55 The e-Commerce operator need not be enabled for e-Invoicing.
4.56 The e-Invoices generated by e-Commerce operators should include “EcmGstin” attribute and should be the same as their GSTIN.
4.57 For e-Invoices generated by Suppliers, the “EcmGstin” attribute should be blank.
4.58 The e-Invoices generated by e-Commerce operators are also accessible to the Suppliers for all the operations such as Viewing of IRN, Cancellation of IRN and Generation of E-Waybill.
4.59 E-Waybills generated by e-Commerce operators can be cancelled by Suppliers also.
4.60 Only e-Commerce operators can generate e-Invoices pertaining to e-Commerce transactions.

Validations on Items:
4.61 Serial number of the item can be only numeric & is verified for duplicate values.
4.62 Each item needs to have valid HSN code with at least 4 digits. HSN Code should be valid as per the GST master.
4.63 If Is Service is selected, then the HSN codes must belong to services.
4.64 Each item should have valid Unit Quantity Code (UQC) as per the master codes, in case of goods.
4.65 Quantity and Unit Quantity Code are mandatory for Goods and optional for Services.
4.66 Tax rates are being validated. Only the allowed tax rates will be accepted for all types of document including Credit Note and Debit Note. In case of intra-state transaction, the sum of SGST and CGST tax rates should be entered as GST Rate.
4.67 In case of inter-state transaction, the IGST tax rate and value has to be passed.
4.68 In case of export transaction, IGST tax rate and value has to be passed.
4.69 In case the Recipient is SEZ unit or SEZ Developer, then IGST tax rate and value has to be passed irrespective of state of the Recipient.
4.70 Maximum number of items in each invoice should not exceed more than 1000 items and a minimum of 1 item should be available.


Calculation of Values:
4.71 The following summation validations are to be done for items
4.72 Taxable Value of Item = Gross Amount of Item - Discount
4.73 SGST Value of Item = Taxable Value of Item X GST Rate / 2, if intra-state CGST Value of Item = Taxable Value of Item X GST Rate / 2, if intra-state
4.74 IGST Value of Item = Taxable Value of Item X GST Rate, if inter-state
4.75 Cess Value of Item = Taxable Value of Item X Cess Rate
4.76 State Cess Value of Item = Taxable Value of Item X State Cess Rate
4.77 Total Value of Item = Taxable Value of Item + SGST Value of Item + CGST Value of Item + IGST Value of Item + Cess Value of Item + State Cess Value of Item + Non-Advol Cess Value of Item + State Cess Non-advol value of Item + Other charges.
4.78 However, in case of Reverse charge and Export transactions (EXPWP), Total value of Item can match with either with tax values or without tax values. That is, the total value of item can include or exclude the tax values as per the business requirements.
4.79 (Note: Temporarily, the validation of 'Gross Amount of Item with Quantity and Selling Unit Price' has been withdrawn.
4.80 In case of EXPWOP and SEZWOP, Passed IGST Value of Item will not be validated even if actual tax rate is passed, if the passed value of IGST for that is ZERO.)
4.81 In case of Reverse Charge, the tax (SGST+CGST or IGST) may be included or excluded in the Total value of Item.

4.82 The following summation validations are to be done on Invoice total
4.83 Total Taxable Value = Taxable Value of all Items
4.84 Total SGST Value = SGST Value of all Items
4.85 Total CGST Value = CGST Value of all Items
4.86 Total IGST Value = IGST Value of all Items
4.87 Total Cess Value = Cess Value of all Items + Non-Advol Cess Value of all Items
4.88 Total State Cess Value = State Cess Value of all Items + State Cess Non-advol Value of all Items
4.89 In case of CREDIT NOTE AND DEBIT NOTE, the ‘IGST/CGST/SGST/CESS value of item’ is not validated with corresponding tax rates and taxable values.
4.90 Tolerance limit for points 1 and 2 above: The passed value should be between minimum and maximum values as explained here. Minimum value is considered as the rupee part of the calculated value minus one rupee and maximum value is taken as the rounded up to next rupee value of the calculated value plus one rupee.
4.91 Example 1: In Point 1 and 2, if calculated value for IGST of item A is 2345.04 then tolerance limit for passed value of that item is between 2344.00 and 2347.00.
4.92 Example 2: In Point 1 and 2, if calculated value of IGST of all items is 10241.00 then tolerance limit for passed value of IGST of all items is between 10240.00and 10242.00
4.93 The round-off value for 'Round_off_amount' attribute is to adjust final 'Total_Invoice_Value_INR' attribute and can be between -99.99 and +99.99
4.94 The following summation validation is to be done on Invoice total
4.95 Total Invoice Value = Sum of All Total Value of Items - Invoice Discount + Invoice Other charges + Round-off amount
4.96 Tolerance limit for point 5 above: The passed value should be between minimum and maximum values as explained here. Minimum value is considered as the rupee part of the calculated value minus one rupee and maximum value is taken as the rounded up to next rupee value of the calculated value plus one rupee.
4.97 Example : If ‘calculated total invoice value’ is 10241.61 then tolerance limit for ‘passed total invoice value’ is between 10240.00 and 10243.00

Validations on e-waybill:
4.98 E-waybill can be generated only if E-way Bill related details are passed where distance is mandatory.
4.99 E-way Bill is not generated for document types of Debit Note and Credit Note and Services.
4.100 E Way Bill can be generated provided at least HSN of one item belongs to goods.
4.101 If only Transporter Id is provided, then only Part-A is generated. Transport Mode, Vehicle Type, Vehicle No, Transportation document number and date should be null or attributes should not have been passed.
4.102 If mode of transportation is "Road", then the Vehicle number and vehicle type should be passed. If mode of transportation is Air, Rail, then the transport document number and date should be passed. Vehicle type and vehicle number should be null or attributes should not have been passed.
4.103 If mode of transportation is “Ship/ Road cum Ship”, then either Vehicle number or transport document number and date or both can be passed. Vehicle type should be ODC.
4.104 The Vehicle no. should match with specified format and exist in Vahan database.
4.105 E-Waybill will not be generated if the Supplier or Recipient GSTIN is blocked due to non-filing of Returns.
4.106 Pincode of Recipient GSTIN is mandatory if Ship-To details are not entered.
4.107 The distance of transportation is validated against the auto-calculated PIN-PIN distance stored in the system. The allowed distance for transportation should be between +/- 10 % of auto-calculated PIN-PIN distance. If the auto-calculated distance is less than 100 KMs, then The allowed distance for transportation should be between 1 and +10 % of auto-calculated PIN-PIN distance.
4.108 If the distance of transportation is passed as 0 (zero), then the system will consider it as request made by the tax payer, to consider the auto-calculated PIN-PIN distance for the generation of e-way bill and generate the e-way bill along with IRN. The actual distance is passed in “Info. Message” column for reference.
4.109 If the PIN-PIN distance is not available in the system, the passed value of distance will be taken for generation of e-way bill and distance value can not be more than 4000.
4.110 The actual distance has to be passed in case the source and destination PIN codes are same and the allowed range of value is from 1 to 100.
4.111 In case of export of goods, if e-way bill has to be generated, then the address of port should have been passed as shipping address during generation of IRN.
4.112 In case incomplete information has been passed for generation of E Way Bill, then IRN will be generated and returned but not E Way Bill number. However subsequently, based on IRN, E Way Bill can be generated.

7. Get IRN deatils by Doc. deatils
Overview
This method provides the Get IRN details for a given doctype, docnum & docdate.

The format and details of Get IRN details by Doc. Details API request is depicted in following table.

URL	             <URL>/irnbydocdetails?doctype=/<Doc. Type>&docnum=<Doc. No.>&docdate=<Doc. date>
Content-Type     application/json
Method           GET
URL Parameters   Document type, Document number, Document date

Request Payload
Request Header

Attributes	      Description
client_id	      client id to be provided by E-Invoice System
client_secret     client secret to be provided by E-Invoice System
Gstin             GSTIN of the authenticated user
sup_gstin         (Optional) Supplier GSTIN, only in case E Comm. operator is getting IRN details. For RCM invoices recipient GSTIN to be passed
user_name         User name of the authenticated user
AuthToken         Authentication token returned by the E-Invoice system

Response Payload
Attributes	       Description
Status	           Status of the GET e-Invoice details request(values 1-Success and 0- Failure)
Data	           If Status is ‘1’
ErrorDetails	   If Status is ‘0’
InfoDtls	       Any additional message to be conveyed would be passed.


If Status is "1"
Data	     Base 64 encoded string of decrypted invoice JSON using Sek.
After decrypting Data the following attributes are obtained as below.

Attributes	           Description
AckNo	               Transaction number
AckDt	               Date and time on which invoice is registered(Date format is ‘yyyy-MM-dd HH:mm:ss ’).
Irn	               SHA256 hash of Gstin, DocDtls.No, DocDtls.Typ, financial year of DoctDtls.Dt
SignedInvoice	       Complete e-Invoice data digitally signed using JSON Web Token(JWT) and JSON Web Signature (JWS) with “SHA256RSA” algorithm
SignedQRCode	       Complete QR- Code data digitally signed using JSON Web Token(JWT) and JSON Web Signature (JWS) with “SHA256RSA” algorithm
Status	                ‘ACT’ for Active and ‘CNL’ for Cancelled
EwbNo	              E Way Bill No. , if E Way Bill is generated
EwbDt	              E Way Bill Date. , if E Way Bill is generated
EwbValidTill	      E Way Bill validity date, if Part B details are provided in the payload
Remarks	              Additional information such as, If distance is passed is 0, shows actual distance calculated for the pair of PIN codes


If Status is "0"
ErrorDetails	Base 64 encoded string.
On decoding ErrorDetals the following attributes from JSON array are obtained as follows.
ErrorCode	    Unique error code
ErrorMessage	Error Description

Invoice Management System (IMS)
Frequently Asked Questions: Invoice Management System (IMS)
1Q. What is Invoice Management System (IMS)?
1A. Invoice Management System (IMS) is a facility in GST
system, where the invoices/records saved/filed by the
supplier in GSTR-1/1A/IFF, can be accepted, rejected or
kept pending by recipients in order to correctly avail
ITC.
2Q. How can I access IMS?
2A. IMS can be accessed using below path on GST Portal :
Dashboard > Services > Returns > Invoice
Management System (IMS) Dashboard.

3Q. When will IMS be made available to taxpayers?
3A. IMS will be launched on the GST Portal from 1st October
2024 and shall be available to the taxpayers for taking
actions on the received invoices/records from 14th
October 2024 onwards.

4Q. What all records will be available in IMS for taking an action?
4A. All the saved or filed original invoices/records and
their amendments by suppliers through GSTR1/1A/IFF will be available to the recipient for taking
actions in IMS. However, the documents where ITC is
not eligible either due to:
i. POS rule or
ii. Section 16(4) of the CGST Act,
will not appear on IMS and will directly go to ‘ITC Not
Available’ section of GSTR-2B.

5Q. What will happen to the accepted and rejected record?
5A. All the accepted/rejected records belonging to a
particular GSTR-2B period will be removed from IMS
on filing of GSTR-3B for that particular period. Only the
pending record and the invoices/records belongs to
future tax period shall remain in IMS.

6Q. When will the documents be flown to IMS?
6A. The documents will be available in IMS as soon as
they are saved by the supplier in their corresponding
GSTR-1/1A/IFF.

7Q. When can the recipient taxpayer take action on an record?
7A. As soon as a supplier/ taxpayer saves an Invoice/
records in GSTR-1/1A/IFF, it is shown and is available
to the recipient taxpayer in IMS for taking actions.

8Q. What all documents will not be made available in IMS but will be part of GSTR-2B?
8A. Below records will not be part of IMS but will directly
flow to GSTR-2B:
1. Document flowing from the following forms:
• GSTR 5
• GSTR 6
2. ICEGATE documents
3. RCM records
4. Document where ITC is ineligible due to:
• POS rules
• Section 16(4) of CGST Act
5. Documents where ITC to be reversed on
account of Rule 37A

9Q. Who will have access to IMS functionality?
9A. Taxpayers registered as normal taxpayers (including
SEZ unit/Developer) and casual taxpayers will be able
to access IMS functionality.

10Q.  What are the actions that I can take on an IMS ?
10A.Below actions are allowed to take in IMS:
i. Accept
ii. Reject
iii. Pending
Note: By default all the records will flow into “No
Action” category and records with “No Action” will be
deemed accepted at the time of GSTR-2B generation.

11Q. Are there any invoices/records where pending action is not allowed in IMS?
11A. Yes, for the following 4 scenarios, pending action
would not be available : -
A. Original Credit note
B. Upward amendment of the credit note irrespective
of the action taken by recipient on the original
credit note
C. Downward amendment of the credit note if original
credit note was rejected by him,
D. Downward amendment of Invoice/ Debit note
where original Invoice/ Debit note was accepted by
him and respective GSTR 3B has also been filed


12Q. Can I take actions multiple time on a document?
12A.Yes, action can be taken multiple times on an
invoice/record before filling of GSTR 3B. In case of
multiple actions on a record, latest action will
overwrite the previous action. However, the action
taken will be frozen at the time of filing the
corresponding GSTR-3B by the recipient.

13Q. What happens to the original Tax Invoice/Debit Note if the same record is amended by the supplier?
13A. If original and amended Tax Invoice/Debit Note
belongs to 2 different GSTR 2B return period, then it is
mandatory to take action on original Tax Invoice/Debit
Note and file the respective GSTR 3B before taking
action on amended Tax Invoice/Debit Note (amended
through GSTR-1/1A/IFF). In case if recipient take the
action on amended Tax Invoice/Debit Note first then
system will not allow to save the action in IMS.
In case both the original Tax Invoice/Debit Note and
amended Tax Invoice/Debit Note belong to same
period GSTR-2B, the action taken on amended Tax
Invoice/Debit Note will prevail over the action taken
on original Tax Invoice/Debit Note. However, you need
to first bring the original invoice/ debit note from
pending status to either accept or reject status before
taking action of amended invoice/debit note as
otherwise system will not allow you to take any action
on amended invoice.

14Q. What happens to the original Credit Note if the same is amended by the supplier?
14A. If original and amended credit note both are available
in IMS whether it belong to two different GSTR-2B
period or same GSTR-2B period, the action taken on
amended credit note will prevail over the action taken
on original credit note.

15Q. What will happen to documents on which taxpayers has taken an action on IMS?

based on different kind of action:
i. Accept –Accepted records will become part of
‘ITC Available’ section of respective GSTR 2B.
ITC of accepted records will auto-populate in
GSTR 3B.
ii. Reject –Rejected records will become part of
‘ITC Rejected’ section of respective GSTR 2B.
ITC of rejected records will not auto-populate in
GSTR 3B.

17Q. What If I have taken an action on a document in saved status but the same is edited/changed by the supplier before filing his GSTR-1?
17A. In case a saved record is edited before filing of GSTR-1

21Q. What will happen to the documents in IMS on filing of GSTR 3B by recipient?

24Q. What is draft GSTR 2B? 
24A. 2B will continue to be generated on 14th of every month with the same logic as current GSTR-2B which will now be considered as draft GSTR 2B. This draft will consist of all the accepted / deemed accepted

25Q. Can I take any action after generation of draft GSTR 2B?
25A. Yes, the recipient will be allowed to take an action on

26Q. Is there any scenario where draft GSTR 2B will not be generated by system on 14th of subsequent month?

GSTR 3B.

27Q. How many times can I regenerate GSTR 2B?

The Invoice Management System (IMS) lets a recipient act on invoices, debit notes, and credit notes that suppliers have uploaded. For each record the recipient chooses one of three actions:
Accept: The record is confirmed. The recipient can claim ITC on it in GSTR-2B, and the supplier's liability in GSTR-3B reflects the record.
Reject: The record is refused. The recipient gets no ITC from it, and the supplier's liability does not include it.
Pending: No decision yet. The record stays open, and it does not change ITC or liability until the recipient acts.

The two impact columns show:
Impact on R2B ITC: how much ITC the recipient can see in GSTR-2B, based on the action on the original record and on the amendment record.
Supplier 3B liability: how the supplier's tax liability in GSTR-3B changes.

Record types covered:
B2B invoices, debit notes (DN), and ECO records: Original records.
B2BA/DN and B2BA/DNA: Amendments to an invoice or debit note. "Upward" increases the value, and "Downward" decreases it.
CN and CNA: Credit notes and their amendments, with the same upward and downward split.
RCM to FCM and FCM to RCM: Changes between reverse charge (the recipient pays tax) and forward charge (the supplier pays tax).

1. Invoice, debit note, and ECO records (original)
Accept: The recipient gets full ITC in GSTR-2B, and the supplier's liability increases by the full amount.
Reject: The recipient gets no ITC, and the supplier's liability does not change.
Pending: Nothing changes for ITC or liability until the recipient decides.

2. Upward amendment (B2BA/DN)

An upward amendment increases the original value, and the increase is called the delta. Its result depends on the action taken on both the original and the amendment.
Original accepted, amendment accepted:The recipient gets full ITC on the original plus the delta on the amendment. The supplier's liability increases by the delta.
Original accepted, amendment rejected: The recipient keeps ITC on the original amount only. The delta gets no ITC, and the supplier's liability does not include it.
Original accepted, amendment pending: The original ITC stays. The delta waits until the recipient acts on the amendment.

3. Downward amendment (B2BA/DNA)

A downward amendment reduces the original value.
Original accepted, amendment accepted:The recipient's ITC reduces by the delta. The supplier's liability reduces by the same amount.
Original accepted, amendment rejected: The ITC is not reduced, so the recipient keeps the full original ITC. The supplier's liability increases by the delta, because the reduction was not accepted.
Original accepted, amendment pending: The table marks this combination as not allowed, so the supplier cannot leave a downward amendment pending in this case.

4. Credit note (CN)

A credit note reduces the value of an earlier invoice.
Accept: The recipient's ITC reduces by the full amount, and the supplier's liability reduces by the full amount.
Reject: The recipient's ITC is not reduced. The supplier's liability increases by the full amount, since the reduction was not accepted.
Pending: Not allowed for this record type.

5. Credit note amendments (CNA)
Upward CNA: This increases the credit already given.
Accept on both original and amendment: The recipient's ITC reduces by the delta, and the supplier's liability reduces by the delta.
Reject on the amendment: The ITC stays, and the supplier's liability increases by the delta.
Pending: Not allowed, or not applicable, depending on the combination in the table.
Downward CNA: This reduces the credit already given.
Accept on the amendment: The recipient's ITC increases by the delta, and the supplier's liability increases by the delta.
Reject on the amendment: The ITC is not increased, and the supplier's liability does not change for the delta.
Pending: Not allowed in the cases the table marks as such.

6. RCM to FCM (reverse charge changed to forward charge)
Invoice or debit note, accepted: The recipient gets full ITC, and the supplier's liability increases by the full amount. The supplier now pays the tax.
Invoice or debit note, rejected: No ITC, and no liability change.
Invoice or debit note, pending: No change until the recipient acts.
Credit note, accepted: The recipient's ITC reduces by the full amount, and the supplier's liability reduces by the full amount.
Credit note, rejected: The supplier's liability increases by the full amount.

Credit note, pending: Not allowed.

7. FCM to RCM (forward charge changed to reverse charge)

Invoice or debit note, accepted: The supplier's liability reduces by the full amount, because the recipient now pays the tax. The recipient's ITC is reported under sections 3.1(d) and 4A(3) of GSTR-3B, rather than as normal ITC.

Invoice or debit note, rejected: No change to ITC or supplier liability.

Invoice or debit note, pending: No change until the recipient acts.

FCM credit note to RCM credit note, accepted: The table shows the credit note changing both the ITC position and the supplier's liability by the full amount. Check the exact treatment in the official FAQ, because this row is hard to read in the copied text.
